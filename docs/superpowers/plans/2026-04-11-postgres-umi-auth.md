# Postgres UMI Auth Migration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace password-based PostgreSQL auth with User-Managed Identity (Entra ID) by fixing an `IsPublishMode` guard, adding the `Npgsql.Azure` token provider, and wiring a KEDA `TriggerAuthentication` to use `azure-managed-identity` — eliminating all postgres secrets from ACA and fixing `KEDAScalerFailed`.

**Architecture:** `AddAzurePostgresFlexibleServer` in Aspire 13.2.0 already defaults to Entra ID. The bug is that `RunAsContainer()` fires during `aspire publish` because it lacks an `!IsPublishMode` guard, causing Aspire to emit a Docker container instead of a Flexible Server. Fixing the guard + adding `Npgsql.Azure` for token-based DB auth + a new KEDA Bicep module completes the migration.

**Tech Stack:** .NET 10, Aspire 13.2.0, Npgsql 10 + Npgsql.Azure, Azure Database for PostgreSQL Flexible Server, Azure Container Apps, KEDA postgresql scaler, Bicep

**Spec:** `docs/superpowers/specs/2026-04-11-postgres-umi-auth-design.md`

## Task 2: Fix `RunAsContainer()` Publish Guard in AppHost

**Files:**
- Modify: `backend/MfePortal.AppHost/Program.cs` (lines ~190–195)

**Background:** `AddAzurePostgresFlexibleServer` defaults to Entra ID. The current code calls `postgres.RunAsContainer(...)` inside `if (builder.Environment.IsDevelopment())`. When you run `aspire publish` locally, `IsDevelopment()` is true, so `RunAsContainer()` fires and Aspire emits a Docker container (`container.v1`) instead of a `Microsoft.DBforPostgreSQL/flexibleServers` resource. The fix: add `&& !builder.ExecutionContext.IsPublishMode` to the guard — same pattern as the Dapr and k6 guards already in this file (lines ~74, ~149, ~175, ~270).

- [ ] **Step 2.1: Update the `RunAsContainer` guard**

  In `backend/MfePortal.AppHost/Program.cs`, find:

  ```csharp
  if (builder.Environment.IsDevelopment())
  {
      postgres.RunAsContainer(c => c.WithEnvironment("POSTGRES_INITDB_ARGS", "--encoding=UTF8"));
  }
  ```

  Replace with:

  ```csharp
  if (builder.Environment.IsDevelopment() && !builder.ExecutionContext.IsPublishMode)
  {
      postgres.RunAsContainer(c => c.WithEnvironment("POSTGRES_INITDB_ARGS", "--encoding=UTF8"));
  }
  ```

## Task 3: Wire `UseAzure` Token Provider into `AddNpgsqlDbContext`

**Files:**
- Modify: `backend/MfePortal.AppHost/../AugmentService/AugmentService.Api/Program.cs` → actually `backend/AugmentService/AugmentService.Api/Program.cs` (lines ~116–125)

**Background:** When the connection string contains `Authentication=ManagedIdentityAuthentication`, Npgsql expects a token provider to supply the password. `UseAzure(credential)` on `NpgsqlDataSourceBuilder` registers that provider. It calls `DefaultAzureCredential.GetTokenAsync` for scope `https://ossrdbms-aad.database.windows.net/.default` and passes the token as the Postgres password. The `credential` object is already created at the top of `Program.cs` and shared with Key Vault.

All three `AddNpgsqlDbContext` calls must get `UseAzure` — `ProductDataContext`, `WeatherDatabaseContext`, and `UserDbContext` (the last two both use the `"weatherdb"` connection name).

The `configureSettings` lambda (`s => s.ConnectionString += ";GssEncryptionMode=Disable"`) is removed from all three calls. `GssEncryptionMode=Disable` will be embedded in the Aspire-generated connection string env var value in the Bicep output (Task 4 regeneration handles this).

- [ ] **Step 3.1: Add `using` for `Npgsql.Azure`**

  Open `backend/AugmentService/AugmentService.Api/Program.cs`. At the top of the file with the other `using` statements, add:

  ```csharp
  using Npgsql.Azure;
  ```

- [ ] **Step 3.2: Update all three `AddNpgsqlDbContext` calls**

  Find the existing block (~lines 116–124):

  ```csharp
  builder.AddNpgsqlDbContext<ProductDataContext>(
      connectionName: "productdb",
      configureSettings: s => s.ConnectionString += ";GssEncryptionMode=Disable");
  builder.AddNpgsqlDbContext<WeatherDatabaseContext>(
      connectionName: "weatherdb",
      configureSettings: s => s.ConnectionString += ";GssEncryptionMode=Disable");
  builder.AddNpgsqlDbContext<AugmentService.Infrastructure.Data.UserDbContext>(
      connectionName: "weatherdb",
      configureSettings: s => s.ConnectionString += ";GssEncryptionMode=Disable");
  ```

  Replace with:

  ```csharp
  builder.AddNpgsqlDbContext<ProductDataContext>(
      connectionName: "productdb",
      configureDataSourceBuilder: dsb => dsb.UseAzure(credential));
  builder.AddNpgsqlDbContext<WeatherDatabaseContext>(
      connectionName: "weatherdb",
      configureDataSourceBuilder: dsb => dsb.UseAzure(credential));
  builder.AddNpgsqlDbContext<AugmentService.Infrastructure.Data.UserDbContext>(
      connectionName: "weatherdb",
      configureDataSourceBuilder: dsb => dsb.UseAzure(credential));
  ```

  > **Note:** `credential` is the `DefaultAzureCredential?` created near the top of `Program.cs`. Since it is nullable (null in the Test environment), and `AddNpgsqlDbContext` is already guarded by `builder.Environment.EnvironmentName != "Test"`, `credential` is guaranteed non-null here. If the compiler emits a nullable warning, add the `!` null-forgiving operator: `dsb.UseAzure(credential!)`.

## Task 5: Wire KEDA Postgres Scale Rule via ACA Managed Identity

**Files:**
- Modify: `backend/MfePortal.AppHost/aspire-output/augmentservice/augmentservice.bicep`
- Modify: `backend/MfePortal.AppHost/aspire-output/main.bicep`

**Background:** Azure Container Apps has its own built-in KEDA integration. In ACA, you do **not** deploy raw KEDA `ScaledObject` or `TriggerAuthentication` CRDs. Instead, scaling rules are defined directly on the `Microsoft.App/containerApps` Bicep resource under `template.scale.rules`. For postgres-based scaling with managed identity, the scale rule goes in `augmentservice.bicep` with `identity:` set to the UMI resource ID — no secret reference, no CRD. This is why the original `KEDAScalerFailed` error occurs: the old rule referenced an ACA secret that KEDA's controller can't resolve from outside the container app.

The `augmentservice_identity_outputs_id` param already exists in the regenerated `augmentservice.bicep` after Task 4 (Aspire generates it for the container app's identity block). The two new params (`postgres_outputs_fqdn`, `postgres_outputs_adminlogin`) must be added and wired through `main.bicep`.

  > **Before starting Task 5:** Open the Task 4–regenerated `postgres/postgres.bicep` and check its `output` declarations. Note the exact names for the FQDN output and the admin login name output — they are referenced in Step 5.2 as `postgres.outputs.<name>`. Common Aspire names are `fqdn` and `administratorLogin` (or `adminLogin`). Use whatever names actually appear in the generated file.

  Also confirm that `augmentservice_identity_outputs_id` exists as a param in the regenerated `augmentservice.bicep`, and that its value is the **full UMI resource ID** (a string like `/subscriptions/.../resourceGroups/.../providers/Microsoft.ManagedIdentity/userAssignedIdentities/...`), not just the `principalId` or `clientId` GUID. ACA's `identity:` field in `scale.rules` requires the resource ID string.

- [ ] **Step 5.1: Add postgres scale rule to `augmentservice.bicep`**

  Open `backend/MfePortal.AppHost/aspire-output/augmentservice/augmentservice.bicep`.

  **Add two new params** at the top of the file alongside the existing params:

  ```bicep
  param postgres_outputs_fqdn string

  param postgres_outputs_adminlogin string
  ```

  > `augmentservice_identity_outputs_id` is already present as a param in the regenerated file (used by the identity block). Confirm it exists before continuing — if it is missing for any reason, add it too.

  **In the `template.scale` section**, which currently reads:

  ```bicep
  scale: {
    minReplicas: 1
  }
  ```

  Replace with:

  ```bicep
  scale: {
    minReplicas: 1
    rules: [
      {
        name: 'postgres-scaler'
        custom: {
          type: 'postgresql'
          metadata: {
            host: postgres_outputs_fqdn
            userName: postgres_outputs_adminlogin
            dbName: 'productdb'
            sslmode: 'require'
            targetQueryValue: '5'
            query: 'SELECT COUNT(*) FROM pg_stat_activity WHERE state = \'active\''
          }
          identity: augmentservice_identity_outputs_id
        }
      }
    ]
  }
  ```

  > **If `GssEncryptionMode=Disable` was absent from the connection string values in Step 4.3:** also append `;GssEncryptionMode=Disable` to the `value:` strings for `ConnectionStrings__productdb` and `ConnectionStrings__weatherdb` in the `env` section of this same file.

- [ ] **Step 5.2: Wire the new params through `main.bicep`**

  Open `backend/MfePortal.AppHost/aspire-output/main.bicep`.

  In the `module augmentservice` block's `params`, add:

  ```bicep
  postgres_outputs_fqdn: postgres.outputs.<fqdn-output-name>
  postgres_outputs_adminlogin: postgres.outputs.<adminlogin-output-name>
  ```

  Replace `<fqdn-output-name>` and `<adminlogin-output-name>` with the actual output names you noted from `postgres/postgres.bicep` before starting this task.

  Typical values are `fqdn` and `administratorLogin`. If those exact names exist in the generated file, the params become:

  ```bicep
  postgres_outputs_fqdn: postgres.outputs.fqdn
  postgres_outputs_adminlogin: postgres.outputs.administratorLogin
  ```
